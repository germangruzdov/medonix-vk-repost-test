# МедОникс — тест репоста ВК

Версия 0.5.0 добавляет отдельный эксперимент с процедурой `execute.medonix_repost6311` на сервере самого ВК. Главная обычная ссылка сохраняет сценарий видео 0.3.0; эксперимент HTTP 0.4.0 также сохранён. Для нового режима нужен один ручной шаг в админке приложения 54874242: создать хранимую процедуру medonix_repost6311, вставить содержимое procedures/medonix_repost6311.vkscript.txt и сохранить версию 1. Файл предназначен для редактора VKScript в ВК. Регистрация процедуры и компиляция в ВК ещё НЕ выполнены.

После сохранения: https://vk.ru/app54874242#post=6311&experiment=stored-repost. Фронтенд использует уже проверенные native Bridge чтения wall.getById / likes.isLiked; только запрос записи заменён вызовом execute.medonix_repost6311. Процедура повторно читает точную исходную запись и проверяет copied через likes.isLiked непосредственно перед единственным wall.repost. Ответ published принимается только с корректным post_id, ответ already блокирует повторную отправку, неожиданный ответ или ошибка записи оставляют результат неподтверждённым и блокируют повтор. Предполагается официальный контракт bool_int для copied в ответе VK API.

Внешний сервер-посредник и передача токена на сервер приложения не добавлены. Токен используется платформой ВК через Bridge. Код процедуры проверяется локально в JavaScript на подмене API; это проверка ветвлений, а НЕ подтверждение совместимости с компилятором VKScript и не реальная мобильная публикация. Описание функции: https://dev.vk.com/ru/mini-apps/settings/development/stored-procedures. Прямое чтение страницы документации инструментом недоступно; вызов execute также представлен в официальном Java SDK ВК. Компиляция и реальные права метода должны быть проверены в ВК.

Мобильный результат 0.4.0: source_request / HTTP_UNAVAILABLE через 257 мс; HTTP-статуса и ответа API нет, wall.repost не вызывался. Отдельная проверка без пользовательского токена для публичного utils.getServerTime вернула HTTP 200, Access-Control-Allow-Methods: POST и отсутствие Access-Control-Allow-Origin для Origin https://germangruzdov.github.io. Это согласуется с CORS, но не доказывает точную причину сбоя конкретного запроса телефона.

Изменены entry.js, index.html, repost-core.js, repost.js, privacy.html, package.json, README.md; добавлены vk-procedure.js, procedures/medonix_repost6311.vkscript.txt и tests/procedure.test.mjs. Прежние реальные отказы CLIENT_11 не переинтерпретируются как разрешение API: процедура не расширяет выданные права и может получить отказ ВК.

Версия 0.4.0 добавляет отдельный эксперимент настоящего репоста через прямой HTTPS POST к `https://api.vk.com/method/`. Пользователь 04.11.2026 явно разрешил передачу временного пользовательского токена с правом wall напрямую в официальный API для проверки записи и одного запроса wall.repost после нажатия кнопки. Реальный мобильный результат этого эксперимента ещё не подтверждён.

Ссылка теста: https://vk.ru/app54874242#post=6311&experiment=http-repost. Обычная ссылка без experiment сохраняет сценарий 0.3.0 с новой записью и видео. URL размещения в настройках ВК менять не нужно. Маршрут с experiment использует общий контроллер репоста с HTTP-транспортом вместо VKWebAppCallAPIMethod; выдача токена остаётся через штатный VKWebAppGetAuthToken в приложении 54874242. При открытии страницы и до нажатия кнопки токен не запрашивается и API-запросы не выполняются.

Прямой транспорт допускает только wall.getById, likes.isLiked и wall.repost для wall-218885671_6311. Сначала обязательны чтение правильного исходного поста и проверка прежнего репоста. При ошибке чтения, CORS/сети, неподтверждённом состоянии репоста или отсутствии права wall отправка не выполняется. После любой попытки записи запрос в этом открытии страницы блокируется. Автоматических повторов и переключения на другой транспорт нет. Успех требует success=1 и корректного post_id от ВК.

HTTP: credentials=omit, redirect=error, referrerPolicy=no-referrer, POST с URL-encoded телом, таймаут 12 секунд, ограничение ответа 256 КиБ. Токен не попадает в URL, хранилище, наши серверы или диагностику. Сырой error_msg/request_params API отбрасывается; сохраняются только тип и числовой код. CSP разрешает сетевой доступ только к официальному пути API ВК; обычный сценарий 0.3.0 собственных сетевых запросов не добавляет. Между независимыми открытиями общей атомарной защиты от дублей нет.

Изменены index.html, repost-core.js, repost.js, package.json, privacy.html и этот README; добавлены entry.js, vk-http.js и тесты HTTP/маршрута/интерфейса. Реальные права токена на wall.repost и доступность CORS должны проверяться на телефоне. Код 15/20 от API подтвердит ограничение доступа для токена, а HTTP_UNAVAILABLE означает сетевую ошибку или ограничение браузерного доступа; эти случаи нельзя смешивать с прежним CLIENT_11.

Версия 0.3.0 переключает `index.html` на новую запись с видео через штатный `VKWebAppShowWallPostBox`. Прежний эксперимент настоящего репоста сохранён на `repost.html`. В мобильной проверке 0.2.3 он получил `client_error / 11 / Access denied` при выданном праве wall; пользователь подтвердил отсутствие репоста на стене. Это подтверждает отказ текущему вызову, но не устанавливает возможность получения отдельного допуска к API у ВК.

Новый сценарий: открыть зарегистрированное приложение, дождаться проверки видео, нажать «Опубликовать видео на моей стене», проверить вложение в штатном окне ВК и подтвердить публикацию. `video.html` содержит тот же интерфейс, что главная страница. Адрес размещения менять не требуется. Счётчик репостов исходной записи не увеличивается.

`video-core.js` проверяет точную исходную запись и совпадение ID медиа с настройкой кампании. Если вложение имеет тип clip, дополнительно требует подтверждения того же объекта от `video.get`; отказ или неожиданный ответ останавливает сценарий до открытия редактора. Это проверка существования объекта; поддержка его прикрепления и воспроизведения ещё требует реального мобильного теста. После ответа редактора повторное чтение `wall.getById` должно подтвердить выбранное видео в созданной записи; без этого успех не показывается и повторная отправка блокируется. Доступ video отдельно не запрашивается: отказ read-only проверки остаётся явным ограничением сценария.

Изменены `app.js`, `core.js`, `video.html`, `index.html`, `privacy.html`, `package.json`; добавлены `video-core.js`, тесты подготовки/проверки публикации и интерфейса. При отмене штатного окна допускается только явная повторная попытка. Сетевая ошибка или неопределённый результат блокируют повторную публикацию в текущем открытии страницы. Между независимыми открытиями приложения общей защиты от дублей нет: перед повторной публикацией нужно проверить стену.

Версия 0.2.3 различает CLIENT, API и AUTH в коротком коде ошибки. Клиентские `error_reason` и `error_description` восстанавливаются только из закрытого словаря технических слов; остальные слова, числа и идентификаторы скрываются. Полный объект ошибки, токены и параметры запросов не выводятся. Импорты изменённых модулей имеют версию для WebView с кешированием.

Мобильная проверка 0.2.2: разрешение wall получено, исходная запись прочитана, ошибка при wall.repost имеет type=client_error, code=11. Это НЕ подтверждённая ошибка API 11 про тестовый режим. Точная причина клиентского отказа ещё не установлена; настройки размещения по одному этому коду менять не следует. Обновление 0.2.3 диагностическое, успешный репост им не подтверждён. После ошибки отправки запрос остаётся заблокированным; автоматической повторной публикации нет.

Версия 0.2.2 исправляет остановку при отсутствии необязательного поля `reposts.user_reposted` в ответе `wall.getById`: в этом случае выполняется дополнительная проверка `likes.isLiked` и используется её поле `copied`. Известный прежний репост по-прежнему не дублируется. При неопределённом ответе обеих проверок или ошибке дополнительного запроса запись не отправляется. Контракт: https://github.com/VKCOM/vk-api-schema/blob/master/likes/responses.json.

Версия 0.2.1 добавляет безопасную диагностику: при ошибке на экране видны этап операции и короткий код, отдельно различаются выдача права wall, чтение исходной записи и проверка прежнего репоста. Необработанные сообщения ВК, токены, параметры запросов и персональные данные в диагностику не включаются. Это диагностическое обновление; оно ещё не устанавливает причину ошибки в реальном ВК.

Страница должна запускаться внутри зарегистрированного VK Mini App. В обычном браузере публикация отключена. Право wall в мобильной проверке получено; текущий вызов wall.repost отклонён клиентом. Реальная новая запись с видео по сценарию 0.3.0 ещё не подтверждена.

Пароли и секреты приложения не включены. Временный пользовательский токен выдаёт штатный диалог ВК; токен остаётся в памяти страницы, не логируется, не записывается в хранилище и не отправляется на сервер приложения.
